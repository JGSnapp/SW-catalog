# Grant Scout

Grant Scout — это небольшая агентная система для регулярного мониторинга сайтов с грантами и программами финансирования.

Бэкенд запускает отдельного агента для каждого сайта на базе OpenAI Agents Python SDK. Агент сайта умеет искать страницы, читать контент через цепочку reader fallback'ов, вести переиспользуемые заметки, формировать статус-отчет и сохранять найденные гранты в локальное JSON-хранилище. Фронтенд — это single-page dashboard, где в первую очередь показываются найденные гранты, затем настройки, список сайтов, предложения новых источников и `notes` / `status` по каждому сайту.

## Что умеет система

- Запускает отдельного агента для каждого настроенного сайта.
- Выполняет запуск агентов по расписанию каждые `n` часов.
- Поддерживает принудительный запуск `Run now` из интерфейса.
- Хранит структурированную базу грантов в JSON, а `notes` и `status` по каждому сайту в текстовых файлах.
- Использует предыдущие заметки и последний статус при следующих запусках.
- Отправляет Telegram-уведомления о новых найденных грантах, если настроены переменные Telegram.
- Для каждого гранта сохраняет пояснение, почему он подходит профилю компании, и краткую инструкцию, как его получить.
- Позволяет фильтровать гранты по статусу, направлению, ключевым словам и вести статусы обработки.
- Позволяет настраивать поиск через отдельные поля: институты, направления, суммы, типы финансирования, регионы, дедлайны, условия и ограничения.
- Поддерживает отдельный агентный поиск новых площадок грантов: агент ищет, проверяет и предлагает новые источники, которых еще нет в постоянном списке.
- Дублирует в Telegram как новые гранты, так и новые потенциальные источники грантов.

## Runtime-хранилище

Бэкенд хранит данные в `./data`:

- `data/config.json`
  Глобальные настройки: профиль компании, промпт, расписание, число итераций и список сайтов.
- `data/grants.json`
  Найденные гранты: институт, сумма, тип финансирования, направление, условия, ограничения, дедлайн, ссылка на заявку, источник, статус обработки, пояснение релевантности и инструкция по подаче.
- `data/source_candidates.json`
  Предложенные новые источники грантов: название, URL, причина, подтверждающие наблюдения, статус (`new`, `added`, `dismissed`) и отметка Telegram-уведомления.
- `data/notes/<site_id>.txt`
  Переиспользуемые заметки по сайту для будущих запусков.
- `data/status/<site_id>.txt`
  Последний отчет по сайту.
- `data/notes/__source_discovery__.txt`
  Переиспользуемые заметки агента поиска новых источников.
- `data/status/__source_discovery__.txt`
  Последний отчет агента поиска новых источников.
- `data/runs/<run_id>.json`
  Журнал запусков.

## Чтение страниц и fallback'и

Для чтения конкретной страницы agent-server использует `read_url()` из `agent_server/tools/jina_reader.py`.

Порядок чтения:

1. **Jina Reader**
   URL преобразуется в `JINA_READER_BASE_URL + <target_url>`, по умолчанию `https://r.jina.ai/<target_url>`. Если Jina возвращает успешный ответ, агент получает текст напрямую.
2. **Direct HTTP reader**
   Если Jina не смогла прочитать страницу, а `DIRECT_READER_ENABLED=true`, backend делает прямой `httpx`-запрос с browser-like headers, следует редиректам и очищает HTML через Trafilatura.
3. **Playwright reader**
   Если direct reader тоже не дал текст, а `PLAYWRIGHT_READER_ENABLED=true`, backend открывает страницу в headless Chromium через Playwright, дожидается `networkidle`, забирает HTML и очищает его через Trafilatura.

Ошибки каждого неудачного reader'а сохраняются в `fallback_errors` у успешного fallback-результата. Если все reader'ы упали или извлекли пустой текст, tool возвращает агенту структурированную ошибку, а прогон продолжается.

Важно: успешный HTTP-ответ не всегда означает полезный контент. Например, хостинг может вернуть страницу `Account Suspended` со статусом `200`. Агент должен учитывать содержимое текста, а не только код ответа.

## Веб-поиск и fallback-поведение

`search_web()` использует XMLSearch/XMLStock-совместимый endpoint из `XMLSTOCK_GOOGLE_URL`.

Поведение поиска:

- параметры исходного endpoint сохраняются, а query-параметры `query`, `groupby`, `maxpassages`, `lr` добавляются или переопределяются;
- `maxpassages` ограничивается диапазоном `1..5`;
- XML-ответ парсится через стандартный `xml.etree.ElementTree`;
- из каждого результата извлекаются `title`, `url` и до `maxpassages` текстовых passage;
- если сервис возвращает временные XML-коды `210`, `202` или `110`, backend делает retry с паузой 5-10 секунд;
- по умолчанию выполняется до 8 попыток;
- если ответ не XML, backend возвращает ошибку с preview первых символов ответа;
- если XML содержит финальную ошибку сервиса, она передается агенту как tool error.

Поиск сам по себе не считается парсингом сайта: агент сначала получает кандидаты URL через `search_site_web()`, затем проверяет конкретные страницы через `read_site_url()`.

## Инструменты агента

Каждому site-agent доступны следующие tools:

- `read_site_url`
  Читает URL через reader-цепочку: Jina Reader → direct `httpx` + Trafilatura → Playwright + Trafilatura.
- `search_site_web`
  Выполняет поиск через XMLStock / XMLSearch-совместимый XML API.
- `write_notes`
  Полностью заменяет переиспользуемые заметки для текущего сайта.
- `write_status`
  Полностью заменяет последний статус-отчет для текущего сайта.
- `add_grant`
  Сохраняет или обновляет структурированную запись о гранте. Агент должен заполнить не только условия и источник, но и `fit_reason` — почему грант подходит профилю компании, и `how_to_apply` — как податься или получить поддержку. Дедупликация выполняется по связке `site_id`, `source` URL и нормализованного названия.

Агенту поиска новых источников доступны похожие tools:

- `read_site_url`
  Проверяет страницы потенциальных источников через ту же reader-цепочку.
- `search_site_web`
  Ищет новые порталы, институты, агрегаторы и страницы программ.
- `add_source_candidate`
  Сохраняет проверенный источник-кандидат, если его URL еще не встречается среди постоянных сайтов или уже найденных кандидатов.
- `write_discovery_notes`
  Обновляет заметки поиска источников.
- `write_discovery_status`
  Обновляет статус поиска источников.

## Переменные окружения

Скопируйте пример:

```bash
cp env.example .env
```

Основные переменные:

- `OPENAI_API_KEY`
  API-ключ для агентного runtime.
- `OPENAI_BASE_URL`
  Необязательный кастомный base URL для OpenAI-совместимого API.
- `AGENT_MODEL`
  Имя модели, используемой site-agent и агентом поиска источников. По умолчанию: `gpt-4.1-mini`.
- `JINA_READER_BASE_URL`
  Базовый URL reader-сервиса. По умолчанию: `https://r.jina.ai/`.
- `DIRECT_READER_ENABLED`
  Включает fallback чтения напрямую через `httpx` и очистку HTML через Trafilatura, если Jina не смогла прочитать страницу. По умолчанию: `true`.
- `PLAYWRIGHT_READER_ENABLED`
  Включает браузерный fallback через Playwright и Trafilatura после Jina/direct reader. По умолчанию: `true`.
- `XMLSTOCK_GOOGLE_URL`
  Обязательный endpoint XML-поиска для `search_web`.
- `DATA_DIR`
  Путь внутри backend-контейнера для mounted storage. По умолчанию: `/data`.
- `TELEGRAM_BOT_TOKEN`
  Необязательный токен Telegram-бота для уведомлений о новых грантах.
- `TELEGRAM_CHAT_ID`
  Необязательный ID чата, куда бот будет отправлять уведомления.
- `TELEGRAM_API_BASE_URL`
  Необязательный base URL Telegram Bot API. По умолчанию: `https://api.telegram.org`.

Также поддерживаются совместимые proxy-переменные:

- `PROXY_API_KEY`
- `PROXY_BASE_URL`
- `PROXY_MODEL`

Если `OPENAI_API_KEY` не задан, бэкенд использует `PROXY_API_KEY`.

### Telegram-уведомления

Чтобы включить уведомления:

1. Создайте бота через `@BotFather` и добавьте `TELEGRAM_BOT_TOKEN` в `.env`.
2. Напишите боту любое сообщение от нужного аккаунта или добавьте бота в нужный чат.
3. Получите `chat_id`, например через `https://api.telegram.org/bot<token>/getUpdates`.
4. Добавьте `TELEGRAM_CHAT_ID` в `.env` и перезапустите backend.

Уведомление отправляется после успешного прогона по новым грантам текущего запуска. Если Telegram не настроен, прогон не падает: в журнал добавляется событие `telegram_skipped`.

Сообщение по гранту включает название, институт, сумму, тип финансирования, направление, дедлайн, условия, ограничения, описание, пояснение "почему подходит", инструкцию "как получить" и ссылку.

Сообщение по новому источнику включает название, URL, причину, почему компании стоит рассмотреть источник, и краткое подтверждение, что агент проверил.

## Запуск через Docker Compose

Сборка и запуск всех сервисов:

```bash
docker compose -f docker-compose-api.yml up --build
```

Сервисы:

- Frontend: `http://localhost:3000`
- Backend API: `http://localhost:8000`
- Health check: `http://localhost:8000/health`

Остановка:

```bash
docker compose -f docker-compose-api.yml down
```

## Логика фронтенда

Dashboard намеренно упорядочен по приоритету для оператора:

1. Найденные гранты
2. Глобальная конфигурация
3. Поиск новых источников и предложения площадок
4. Список сайтов с ручным запуском
5. `notes` и `status` для выбранного сайта
6. Журнал последних запусков

Из интерфейса можно:

- задать профиль компании и глобальный промпт;
- настроить институты, направления, сумму, тип финансирования, регион, дедлайн, условия, ограничения и ключевые слова;
- настроить `every n hours`;
- настроить `iterations per site`;
- включить поиск новых площадок грантов по расписанию;
- настроить периодичность и число итераций поиска новых площадок;
- запустить поиск новых площадок вручную;
- добавить предложенный источник в постоянные площадки или скрыть его;
- добавить, изменить, включить, отключить и удалить сайты;
- запустить сайт вручную;
- фильтровать и сортировать базу грантов;
- менять статус гранта: новый, просмотрен, подходит, не подходит, заявка подана;
- просматривать последние `notes` и `status` по сайту и по discovery-агенту.

## Замечания по разработке

- Scheduler работает внутри процесса backend и проходит сайты последовательно.
- Ручной запуск возвращает `409`, если сайт уже выполняется.
- Ручной запуск поиска источников возвращает `409`, если discovery уже выполняется.
- `notes` и `status` записываются только агентом через tools; на фронтенде они доступны только для чтения.
- Гранты сохраняются через upsert по `site_id`, `source` URL и названию, поэтому разные программы с одной страницы могут храниться отдельно.
- Источники-кандидаты дедуплицируются по нормализованному URL относительно постоянных сайтов и уже найденных кандидатов.

## Проверка

Полезные локальные команды:

```bash
python3 -m compileall agent_server
docker compose -f docker-compose-api.yml up --build
```

Если нужно запускать backend-тесты локально вне Docker, убедитесь, что в Python-окружении установлены зависимости из `agent_server/requirements.txt`.

## Текущие ограничения

- Scheduler однопроцессный, а активные запуски отслеживаются в памяти.
- Хранилище файловое, без базы данных.
- Расписание и число итераций общие для всех сайтов, а не индивидуальные.
- Фронтенд — single-page dashboard без роутинга.
- Поиск новых источников использует тот же поисковый endpoint и reader-цепочку, поэтому наследует их ограничения, квоты и ошибки.
